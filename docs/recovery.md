# バックアップと復旧

解除後に「バックアップを保存」を押すと、固定snapshotの暗号化ファイルを作る。ダウンロード先で保存を確認してから「保存できました」を押す。確認前や中断中はバックアップ済みとして記録しない。バックアップ中に編集した場合は完了後も「バックアップ後に変更あり」と表示する。

復旧用秘密とバックアップファイルは別々に保管する。復旧用秘密だけではデータを取り戻せない。最後に保存したsnapshot以降の更新と、既にpurge/履歴退役で除去した版は、そのバックアップから復旧できない。

## ネットワークなしの復号

```sh
node apps/recovery/src/main.mjs --backup /path/to/backup.kvault --output /path/to/new-directory
```

秘密は端末から非表示入力する。明示したローカルファイルを使う場合だけ `--secret-file /path/to/secret` を追加する。秘密そのものを引数・環境変数・URLへ書かない。

出力先は存在しないディレクトリに限定する。全体認証・件数・hash・全AEADを検証してから、保持版を `<object-id-hex>-<revision>.bin` として書く。元タイトルとファイル名は平文のindex.jsonで確認する。文書内のファイル名を出力pathに使わない。ディレクトリは0700、ファイルは0600。失敗時は今回作成した出力だけを削除し、既存ディレクトリを上書きしない。

ツールはアプリが使うfetch/HTTP/TCP/TLS/UDP等のネットワーク経路を起動時に拒否する。これは任意の悪意あるコードに対するOS隔離を置き換えるものではない。パッケージと復旧ツール自体も利用者の信頼対象である。

## 別canisterへの復旧

新しい許可ownerを指定した、空の独立ローカルcanisterを用意する。新ownerでログインし「バックアップから復旧」でファイルと秘密を入力する。

clientが全archiveを検証し、元ID・版・epochを保持してstageする。新canisterのvetKEKでVRKを再ラップし、新しい解除credentialを登録してcommitする。旧ownerの認証を失っても旧サーバーの認可を迂回できるようにはしない。旧canisterからのデータ取得が不要な、手元ファイルからの復旧である。

途中失敗のstageは一般APIに表示されず24時間で失効する。低レベルAPIは同じrecord/chunk/commitの再送を扱うが、現在の画面にはページ再読み込み後のrestore再開ウィザードはない。同じIDが予約済みなら上書きせず、期限切れデータの回収または空の復旧先を使う。成功後は新しいバックアップを保存する。
